## 结论与已修复问题

功能拆分、协议目标捕获、失败分类、聊天容量限制和书签加密边界基本合理，
现有测试对单模块覆盖较完整。薄弱处在多个功能共用连接生命周期时的交互，
以及身份模型在 UI 中的使用。本轮修复以下四类问题：

1. **P1：旧切频道操作污染新连接。** 手动加入频道的后台任务在运行时才读取 `session`，
   返回后也未检查原会话；旧成功结果能覆盖新书签的默认频道及密码，旧失败能写入新连接。
   新增测试复现旧完成覆盖新目标/密码；现在在调度前捕获 session/listener，
   调用前复核，结果和恢复收尾在 epoch 下复核所有权；阻塞加入使用可中断调用。
   同时拒绝正在切换时的第二个手动加入。
2. **P1：同身份多客户端打开用户页崩溃。** 私聊目录已处理重复 UID，但用户列表沿用
   身份字符串作为 Compose 行 key；同一身份多开会产生重复 key 异常。
   模拟器新增测试实际复现 `IllegalArgumentException: Key ... was already used`。
   行 key 改为客户端编号，原有按身份保存的音量设置不变；私聊身份不唯一仍禁止发送。
   这是本轮联动审查发现的既有列表问题。
3. **P2：恢复频道后聊天卡在切换状态。** 默认频道/重连自动恢复只清理 Service 的
   `switchingChannelId`，未刷新 ChatStore；快照先于命令返回或加入失败时，频道文字发送
   会一直被禁用。新增成功和失败回归均复现；现在恢复收尾同步聊天上下文。
4. **P2：授予麦克风权限后服务器仍显示静音。** 空闲 PTT 不一定改变 Service StateFlow，
   权限恢复也可能遗留旧权限错误。状态同步现在独立观察权限值，Activity 权限结果和
   回到前台时显式刷新；只清除已解决的权限错误，不清除其他音频失败，不启动空闲 PTT。

频道详情删除时显示不可用、旧详情响应丢弃、文字/Poke 不确定结果不自动重发、
私聊 ID 复用/重复 UID、书签密码退出保留与损坏数据拒写、音频门控起声/尾帧和修订拒收，
均结合代码及现有测试复核。本次未发现另一个需要修改的确定性缺陷；这不是无缺陷保证。
