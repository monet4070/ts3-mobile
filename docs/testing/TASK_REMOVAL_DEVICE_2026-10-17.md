# 任务移除退出：Android 16 真机复现与修正报告

日期：2026-10-17。代码基线为 `bf3abd9` 加当前工作区变更。
设备：Xiaomi 23127PN0CC，Android 16 / API 36。

## 结论

**当前不能把“小米桌面左右划掉后正常退出”标为可用。**
桌面以 `SwipeUpClean` 杀死拥有 TeamSpeak 会话的进程，随后系统在新进程中
创建服务，再交付 `onTaskRemoved()`。新服务没有旧 socket，无法发送旧会话的
`clientdisconnect`。本轮在省电策略“无限制”、最近任务未加锁/已加锁两种状态下
均复现；加锁不能作为解决办法。

与此同时，当前退出协议在真实服务器上可用：修正版的三次应用内断开、三次通过
Android 框架移除任务，均收到服务器对本客户端的离开通知。它们不能替代小米桌面
划卡手势的验收。用户应先点应用内或通知栏断开，再移除任务，才能在应用仍可执行、
网络正常的情况下完成主动退出。通知栏按钮本轮未单独完成交互验收。

## 起始状态与复现

手机原有两个独立包：主应用和此前安装的 taskremoval 测试应用。主应用显示 M10，
但实际 APK 的 `TeamSpeakService` 没有 `onTaskRemoved` 方法；测试应用的代码与
数据并未覆盖主应用。原包已备份到本地忽略目录。

核对签名证书后，确认本机构建与主应用证书一致；使用 `adb install -r` 保留数据
更新主应用，没有卸载、清除数据或替换 Android Keystore 身份。更新后使用原有
成功服务器历史完成连接，无需写入或公开服务器地址、密码和身份材料。

先安装当前未修正退出顺序的代码，并通过小米桌面左右滑动移除应用卡片。
确认卡片消失后，系统日志显示旧进程被 `SwipeUpClean` 杀死，新进程随后启动。
诊断顺序为：

```text
旧进程：CONNECTED
系统：am_kill ... SwipeUpClean
系统：am_proc_died
系统：新进程启动
新进程：SERVICE_CREATED
新进程：PREVIOUS_PROCESS_EXIT 13
新进程：TASK_REMOVED
新进程：EXIT_STARTED
新进程：EXIT_NO_ACTIVE_SESSION
```

在修正版上再次执行同一桌面操作，也得到相同结果：回调出现在杀进程后
1,527 毫秒，没有 `EXIT_REQUEST_SENT`，卡片已移除。这个证据比“没有看到日志”
更明确：确实执行了回调，但执行它的进程不再拥有旧会话。

一次只移除 TS3 自己的卡片，没有使用会清理其他应用的“全部清理”。
竖直滑动未移除该设备的任务卡片，不计为测试；有效操作均为左右滑动。

## 代码修正与架构边界

此前退出顺序为：停止音频 → 等待会话锁 → 发送退出 → 释放 socket。
音频驱动或旧操作占用锁时，可能消耗整个两秒预算，使退出命令根本没有发出。
新增回归先在旧实现失败：1.5 秒清理减少了协议预算，2.5 秒清理令协议调用次数为零。

修正后的顺序为：

1. 协调器同步登记退出所有权、使旧回调失效并解除旧 socket 的语音源。
2. 对独占捕获的会话执行有期限的协议退出，释放该 socket。
3. 等待旧操作释放会话锁，并行清理采集、播放和路由。
4. 仍由原退出 job 作为新连接使用共享音频资源前的屏障。

`SessionExitRunner` 保持单一职责，未扩大协调器或引入全局状态。现有超长协调器和
测试文件仅同步时序断言；继续保留独立协作者的拆分方向，本轮不混入大规模重构。
未修改公共协议 API、身份/历史存储格式、依赖、权限或 Home/锁屏策略。

服务器退出结果与本地清理结果分开记录：已经确认的服务器退出，不会因稍后音频
超时而变成 `EXIT_TIMED_OUT`；清理失败使用新增固定类别 `EXIT_CLEANUP_FAILED`，
耗时仍使用 `EXIT_CLEANUP_OVERRUN`。日志不包含异常消息或连接信息。
握手中的连接仍直接关闭，不伪造正常退出确认。

## 实测结果

| 场景 | 次数/结果 | 证据与限制 |
| --- | --- | --- |
| 修正版应用内断开 | 3/3 确认 | 点击后 11/9/7 ms 写出退出请求，82/46/38 ms 收到自身离开通知 |
| 修正版 Android 框架移除任务 | 3/3 确认 | 回调后 29/36/32 ms 写出请求，107/121/80 ms 收到自身离开通知 |
| 小米桌面左右划卡，任务未锁定 | 失败 | 修改前、修改后均先杀进程，再向新服务交付回调 |
| 小米桌面左右划卡，任务已锁定 | 失败 | 同样先杀进程；测试后恢复未锁定状态 |
| Android 省电策略 | 原已为无限制 | 未修改此设置；该设置没有阻止 `SwipeUpClean` |
| Home 对照 | 通过 | 原进程保持、无任务移除事件，连接继续运行 |
| 新建服务/重新打开 | 无隐式连接 | 直到手动点击连接才发起新请求 |
| 最终清理 | 已主动断开 | 最后再次收到服务器确认，没有故意留下活动会话 |

框架移除使用 `am stack remove`，每次先验证目标根任务只对应主应用；它绕过小米
桌面的清理入口，不能冒充实际左右划卡。服务器确认取自真实协议的自身离开通知，
不是本地 UI 状态，也不是 UDP ACK。本轮没有另一台客户端的聊天窗口文字截图。

## 交付与剩余限制

主应用已保留数据更新为修正版 Debug APK，独立测试包保留，没有发布 Release。
任务锁定恢复原来的未锁定状态；最终服务器会话已主动断开。

对这台手机，普通应用没有可靠的“被直接杀死之前”回调。不能在进程死亡后通过
补发旧会话退出解决它，也不能靠更长预算或更多重试改变既成的进程终止顺序。
本轮未使用 root、厂商私有权限、常驻辅助应用、保存会话密钥或伪造音频保活。
不应为了猜测划卡而在 `onStop` 断开，否则按 Home、切换应用和锁屏也会断开。

因此，M11 的真实桌面移除退出验收仍未通过，其他长时间、蓝牙、第二设备和
强制停止场景也没有被本轮检查替代。
