# Wi‑Fi ↔ 蜂窝切网失败排查（2026-11-28）

## 实机证据

- 第一轮 Android 已切换到蜂窝。旧会话退出后，自动重连连续尝试 5 次，均在约 0.15–0.21 秒内失败。手动连接后的播放不计入自动恢复；当时反方向仅记录用户报告正常。
- 脱敏日志中，部分尝试记录了后台 `IOException → CommandProcessException`，而建连线程记录了 `IOException → InterruptedException`。这不是 10 秒握手超时的证据。旧日志未保留服务器错误码，无法追溯真实拒绝原因，也不能推断五次均为同一种拒绝。
- 后一轮小米 14 / Android 16 的隔离包记录到 11:37:56、11:38:28 两次切网后的自动重连都收到 `serverErrorId=521`，中间 11:38:16 的手动连接成功。应用先看见旧网络丢失和新网络可用，反向则看见网络替换后探测失败。`521` 表示同一身份仍在线；它与之前另一次观测到的 10 秒握手超时不同。

## 已复现并修复的竞态

固定版本的 ts3j 在接收初始化阶段的服务器 `error` 时，先把 socket 状态置为 `DISCONNECTED`，再通过后台回调报告拒绝。状态切换会中断等待中的建连线程；若它先返回，会把拒绝误记为可重试的建连中断。

新处理器在断开前保存拒绝，建连路径优先取得该结果并只上报一次。明确的 `521` 按同身份连接限制分类，即使服务器文本不同；有其他明确错误码时不靠文案推断。不改动协议依赖、公共 API 或存储格式。发布构建仅增加反射构造器保留规则。

## 双向切网自动恢复

正常快速重连不变。只有已连接会话丢失、重连使用不同的已确认默认网络且服务器返回同身份拒绝时，才保留恢复状态、等 60 秒并且网络可用后自动再试一次。仍然失败则停止；用户断开或发起新连接时取消等待。首次连接、同网掉线的身份冲突、密码错误和封禁不进入这一分支。日志 `NETWORK_HANDOFF_RETRY_DEFERRED` 仅保存等待秒数。

旧连接仍健康时继续沿用；成功的切网探测会更新它的网络基线。若 VPN 没向应用暴露默认网络身份变化，该轮不视为确认切网。等待期间可能中断语音，且无法保证服务器在等待结束前清理旧会话。

## 回归与实机复验

- JVM 回归使用回环 UDP socket，并直接驱动固定 ts3j 的初始化状态和错误包处理器，验证即使后台错误回调尚未送达，也不会丢失拒绝原因；同时覆盖回调送达、同身份限制和缺少错误码。测试不连接真实服务器。
- 虚拟时间覆盖直接换网、短暂离线后换网、60 秒等待、无网不发起、取消、第二次拒绝终止和同网不重试。
- 实机复验必须从已建立的 Wi‑Fi 会话切到蜂窝，不点连接按钮，确认发生服务端往返后才算自动恢复。再反向切回 Wi‑Fi 验证。若仍失败，记录 `TS3_DIAG` 的失败类型和 `serverErrorId`（有值才记录），不要导出服务器地址、密码、身份或完整协议消息。签名候选的这个门禁在真机通过前保持未完成。

## 原会话保留（不是自动重连）

- 11:50:38 的小米 14 诊断中，旧默认网络不可用与替代网络可用相隔约 **116 毫秒**。客户端在此间主动进入重连，随后收到 `521`；这一轮不是无缝切换。
- 对未被系统明确阻止的默认网络丢失，客户端现在先保留会话、频道快照和音频，最多等两秒。替代网络在时限内可用时，取消计时并向原会话发只读 `clientinfo`；收到应答且会话仍是当前会话才继续沿用。确实断线、系统阻止、持续无网或探测失败仍走原失败处理。
- 一次性官方 TS3 3.13.9 回环实例中，保持源地址不变而更换 UDP 源端口，原会话的 `clientinfo` 往返成功。另一次改变源 IP 的实验同样未能在新路径上建立对照新连接，不能由此断言服务端是否支持跨 IP 迁移。
- 维护者报告加入保留机制后，切网时语音短暂停顿后自行恢复。此结果未绑定最终签名 APK，也没有双向切换前后的服务端客户端 ID 记录。
- **无缝验收仍未完成。** 双向切换后必须由服务端观察到同一个在线客户端 ID、无离开或重新加入，且原会话仍能完成服务端往返并收发语音。UI 保持在线、手动连接、自动新建会话都不算通过。保留客户端状态不保证切换期间每个语音包都能送达。
