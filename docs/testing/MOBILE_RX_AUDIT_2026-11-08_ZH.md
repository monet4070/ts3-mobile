# 移动网络收听回归排查

日期：2026-11-08。状态：蓝牙空闲误判已复现、修复并通过实体恢复验证；
移动网络的候选版额外退化尚未确认唯一原因。

## 问题与比较基线

用户报告候选版在移动网络收听他人时卡顿、丢语音，亮屏也会发生。
用户另确认：蓝牙耳机的“蓝牙音频中断”提示在稳定版也会出现。

手机安装包实际 SHA-256 为
`d39aae9475eb0c93a918424d10cfec2bdb95181ea6ee189b79ba6cd88a790e3a`，
与正式 v1.0.0 重发包一致。其生产源码为 `edd97c6`，发布标签提交为
`7a1e36e`，两者间是发布文档差异。不能凭同为 code 14 / 1.0.0 判断包身份。
此前 UI 候选是 Debug 包，正式稳定版是 minified Release，需另做同构建类型对照。

当前工作区保留原有未提交 UI 修改；后续修复范围见下文。
实机比较使用独立包名 `io.github.ts3mobile.rxaudit`，不替换正式稳定版。
该隔离包使用新的测试身份；只在手机上复用已保存的连接信息，麦克风关闭。
临时测量器、诊断构建、源码快照及日志均位于忽略的
`build/mobile-rx-audit-2026-11-08/`，敏感设备原始资料只保存在其中 `private/`。

## 架构、影响范围与排查计划

协议 UDP/语音回调经 `ConnectionCoordinator` 的会话边界交给
`OpusAudioPlayer.submit`，进入有界 input queue，再由独立 worker 执行
talker jitter、Opus 解码、混音和 AudioTrack 写入。设备路由和焦点能撤销这条播放链。
Compose UI 不直接处理收包与解码，但共享状态、通知、锁竞争及运行负载仍需检查。

排查顺序是固定发布输入、逐项审阅生产差异、同轨迹弱网对照、相同实体上的
静默真实 worker 对照，最后比较移动网络与实际蓝牙输出。临时诊断日志只定位失效原因，
不作为精确性能测量。真实频道发言内容随时间变化，顺序实测不能视为同一输入的因果证明。
若需要修复，先用独立回归复现，再最小修改；不扩大缓存或关闭防外放保护来掩盖现象。
大型 coordinator 本轮只审阅，不在调查中顺带拆分。
player 约 300 行、service 超过 600 行：本轮保留 worker/焦点/失效所有权，
仅接入播放前的路由恢复，不搬动已有职责；路由策略继续留在独立 router/guard。
后续若继续增加播放器控制，先把焦点及输出准备迁移为独立协作者，逐项保持生命周期回归，
再缩小 player，避免在本次缺陷定位中引入大范围重构。

## 已完成的同输入验证

稳定版源码导出与当前候选分别运行 12 项选定 JVM 测试，全部通过。
11 条十分钟轨迹包含 1/3/5% 丢包、连续丢 3 包、80 ms 乱序/重复、
8 人时钟漂移以及 100/500/5000 ms worker 停顿。
两版打印的解码、过期、PLC 和最大等待指标逐字相同。
另有自适应/固定等待比较、十分钟样本守恒、调度与蓝牙 guard 回归。
这只证明这些确定输入下结果相同，不证明实际手机听感相同。

在 Xiaomi 14 上，用相同临时测量器分别编译稳定版和候选 Debug 音频模块，
运行生产 `OpusAudioPlayer` worker、真实 JNI 编解码，输出为静默 fake sink，
不采集麦克风、不播放音频、不连接服务器。每条轨迹输入 300 包，包含单人、
8 人以及 120 ms 成批到包，同时反复应用未改变的参与者设置。

| 轨迹 | 稳定版 submit P99 | 候选 submit P99 | 两版接收器收到的样本 | 两版过期/预算重置/PLC |
| --- | --- | --- | --- | --- |
| 单人 | 2.341 ms | 2.275 ms | 各 288000 | 全为 0 |
| 8 人 | 1.144 ms | 1.101 ms | 各 288000（混音） | 全为 0 |
| 120 ms 成批到包 | 1.267 ms | 2.364 ms | 各 288000 | 全为 0 |

每条只创建一次输出；最大相邻 write 间隔两版均低于 28 ms。
本轮单次样本不足以比较微小性能差异，也没有测量真实 HAL 或主应用会话锁。
暂未在该测量中发现新增准入路径造成断流，不能将其写成完全排除。
证据为 `network-differential.json`、`runtime-comparison.json` 和各构建/执行日志。

## 实机已观察到的共有异常

正式稳定版的收听会话收到超过 2.2 万语音帧，无重连。
断开时 audio summary 为：stale 1251、invalid 268、budget 3、PLC 9、
drainTimeouts 3、最大 input age 59.99 ms、最大 combined wait 208.96 ms。
诊断页的 dropped 7 是会话回调拒绝数，不是网络丢包率或实际缺音总量。

系统 audio history 记录该稳定版 18:21:04 请求 SCO、18:21:05 建立，
18:22:04 触发 `ScoTimeOutCheck`，随后断开 SCO。
它证明系统曾主动释放蓝牙通话链路，尚不能据此断言无线耳机物理断连或所有断音均由它造成。
保护提示还可能由通信路由回落、建立超时、becoming-noisy 或实际播放路由 guard 触发，
需关联具体失效原因。保护性静音不能无条件自动解除。

首轮候选 Release 的移动网络/蓝牙会话也出现过期包与 AudioTrack 排空超时；
系统 track history 中存在频繁创建/销毁及未写样本即退役的轨道。
正在使用仅增加匿名事件日志的隔离源码快照关联路由回调、全局失效和 timeline 退役，
尚未将轨道变化直接定性为 bug 或本轮改动回归。

## 蓝牙空闲误判的已复现原因与修复

匿名诊断构建于 18:45:00 收到蓝牙路由确认，18:45:59 收到
`communicationBluetooth=false previous=true`；紧接着 router 发布
`safetyMuted=true error=BLUETOOTH_ROUTE_LOST`。当时选中的蓝牙设备仍在可用列表，
播放轨道此前已因无 PCM 排空退役。它与系统 SCO 超时释放的时间一致。
这建立了“空闲 SCO 释放 → 一律按已建立路由丢失处理 → 锁定静音”的调用链。
这条逻辑源自 v1.0.0 的蓝牙保护，候选版沿用，并非新 UI 引入。

修复将**空闲且选中耳机仍可用**的通信路由释放标为内部待恢复状态：立即撤销旧输出与
准入代次，但不锁定用户静音，也不在空闲时循环请求 SCO。下一次有新语音、且播放器先取得
音频焦点之后，才重新申请同一蓝牙路由。新尝试撤销旧 AudioTrack 的蓝牙确认；
在实际输出确认为蓝牙之前持续阻止手机扬声器/听筒写入。

播放期间丢失、耳机移除、becoming-noisy、建立超时和申请失败仍进入原保护性静音，
不会自动清除。用户手动切到扬声器会取消待恢复，不会被晚到的蓝牙回调抢回。
旧构造函数保留，增加可选的播放前恢复入口；无权限、依赖、存储或配置格式迁移。

生产涉及 audio router/平台监视器/guard/player 与 service 接线；新增独立 JVM 状态回归
及 Android 播放准备顺序回归。

- 225 项 audio JVM、384 项 app JVM 全部通过；新增 6 项覆盖空闲恢复、活动丢失、
  设备已不可用、恢复被拒绝、手动选择与旧输出确认撤销。
- 在忽略的源码副本中临时恢复“一律锁定静音”行为，同一空闲恢复回归如预期失败
  （1 test / 1 assertion failure）；正式实现通过。负向 XML/日志单独保留。
- quality、audio Debug Lint、app Debug/Release Lint、Debug/Release 构建通过。
  Lint 无错误：audio Debug 无 issue；app 原代码仍有 3 Warning/1 Information，
  本轮在线检查另报依赖/AGP 更新建议（合计 Debug 36 Warning/1 Information、

- Xiaomi 14 上 8 项无录音的实体 Android 测试通过，包括新的输出准备顺序、

承载生产 router/player/真实 AudioTrack。无服务器、无麦克风；只在恢复阶段生成零值 PCM。

不计作通过；最终改用上述直接生产对象的实体测量器，避免把自动化控制失败当成产品结论。

`fix-idle-device-probe.log` 和 `idle-device-events.txt`；最终源码/包哈希另存
`fix-source-and-artifacts.json`。CI 常规测试不依赖这台真实耳机或真实服务器。

正式稳定版未被覆盖，实体测试包将在结束后清理；修复未提交、合并或发布。
候选版移动网络额外卡顿不能据此全部归因于蓝牙，仍需要相同语音输入、相同路由和
