# 收听稳定性与延迟档位：调研和执行计划

日期：2026-11-20。状态：已完成首轮离线实验，准备真机听测。门槛是首轮验证建议，不是发布承诺。

## 结论

值得做一个**稳定优先**候选：在相同带宽和编码下，多留几十毫秒来等待抖动中的语音包，减少迟到丢弃、补帧失真和短时断续。先保留**平衡（当前自动）**作为默认；候选达标后再公开，不先把所有人的延迟加大。不要叫「音质优先」：它改善的是收听连续性，并不提高 Opus 码率、蓝牙通话音质或麦克风清晰度。

三项工作分开验证：**接收抖动缓冲**处理包到达时间不均；**设备输出缓冲**只在有证据时处理本机播放欠载；**Wi-Fi ↔ 流量切换**独立排查自动恢复。SCO 路由重建和服务器重新登录都不能靠把缓冲拉大来解决。

## 当前实现有什么缓冲

- [接收策略](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/ReceivePolicy.kt)、[自适应估算](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/AdaptiveJitterDelay.kt)：按讲话人估算，初始 60 ms，目标范围 40–120 ms；64 个连续等时长到包样本提供高分位估算，以 10 ms 调整，稳定后才回落。[每路解码](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/TalkerJitterPipeline.kt)通常在下一段讲话应用新目标；特定缺口可有限补缓冲。调高上限不等于立即多等这么久，也不保证能救回已错过截止时间的包。
- [输入队列](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/VoiceReceiveQueue.kt)的 60 ms 是等待播放 worker 处理的过期剪枝，不是接收抖动目标。[媒体预算](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/ReceiveMediaBudget.kt)把输入、待解码和 PCM 的同一份媒体统一计账：每用户 11,520 样本（48 kHz 下 240 ms）、96 包及字节上限，全局还有编码字节和讲话人上限。不要把这些上限当目标，也不为稳定档直接放宽它们。160 ms 加长包和已有 PCM 可能碰预算，长包、多讲话人要单测。
- [Android 输出](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/AndroidPlaybackOutput.kt)是 48 kHz、单声道 PCM16、低延迟、非阻塞流式写入；创建时的申请容量为系统最小值与 4 个 10 ms 块中较大者。实际容量、有效大小、起播阈值和已写未播帧数是不同量；只改 `setBufferSizeInBytes` 不代表播放队列里实际多了相应的音频。
- [保轨与排空](../../audio-opus/src/main/java/io/github/ts3mobile/audio/opus/PlaybackTimeline.kt)和前述两层缓冲分别负责生命周期、排序以及本机供给。真实路由丢失、耳机保护、静音和代次失效必须仍可立即丢弃旧输出。已有解码限长、短缺口 PLC、重置后淡入、独立增益和混音限幅，首轮不改。根据 [Opus 规范](https://www.rfc-editor.org/info/rfc6716/)，带内 FEC 需要发送端给出冗余；本项目还要求确认包长并在截止前等到后继包。普通 TS3 来流的分帧未确认，不能简单默认开启 FEC；已永久丢失的语音无法靠多等还原。

## 候选方案

### A. 接收档位：先做这一项

| 档位 | 初始 / 下限 / 上限（ms） | 行为 |
| --- | --- | --- |
| 平衡（默认） | 60 / 40 / 120 | 保留当前自适应参数与行为，作为对照及一键回退档。 |
| 稳定优先（实验） | 90 / 70 / 160 | 保留自适应，以更高下限吸收晚到语音；起步比当前多 30 ms，范围上限多 40 ms。实际增加量由相同网络下的落点决定，这些不是端到端延迟。 |

让 `ReceivePolicy` 成为参数的唯一来源，由 `AdaptiveJitterDelay`、每路起播和有限重缓冲共同使用，不只改上限常量。不变更 TeamSpeak 信令、编码、麦克风、60 ms worker 入队期限或已有内存预算。保持短缺口、过载和代次淘汰策略，不因档位变化额外补帧或在活跃语音中突然拉伸。在离线轨迹先扫描更小/中等余量；如果长包或叠加导致更多预算重置，就降低候选上限，不直接抬高所有上限。

实验通过后，在 **设置 → 收听设置 → 播放模式**放两张整行可点的单选卡，不放主界面菜单，也不加独立可点击文字、毫秒滑杆或显而易见的小字。档位本地保存，缺省／未知值回到平衡。首版下一次手动连接生效，同一会话的自动重连沿用已应用档位；只在切换后用一条状态提示说明何时生效，不为设置变更强制断线。更激进的「低延迟」档等测出稳定下限再评估，不先推给用户。

### B. Android 输出：只有量到欠载才做

如果输入、解码和混音连续，仍有 `OUTPUT_UNDERRUNS` 且与设备卡顿对齐，就单独试增加约 **20–40 ms 的实际预填余量**（48 kHz 下 960–1,920 帧），不同时改接收目标。读取实际容量／有效大小／播放头，确认预填真的形成队列，保持非阻塞和每 tick 写入上限。按照 [Android AudioTrack 接口](https://developer.android.com/reference/android/media/AudioTrack)，API 24+ 可在已有容量内调整有效大小，API 31+ 才能读写独立起播阈值。对齐底层返回的实值，旧系统／拒绝调整走原行为；阈值不能使短句卡在起播前，也不能为了预填绕开路由确认、补长静音或伪造播放。优先仅在安全的起播边界应用，检测连续真实写入停滞，避免把预期的背压误报为故障，也不放宽真正的写入超时。

20–40 ms 不能覆盖一次 300 ms 的系统长停顿。若慢调用与反复拆轨仍同步，录制不含语音内容的受控轨迹，分别记录排空、路由不可用、显式失效和输出错误的退役原因，以及创建、启动、写入分阶段耗时；优先修生命周期，不按欠载次数无限加缓冲。不要同时修改低延迟标志、蓝牙编解码器或系统全局音频设置。

### C. 网络切换：独立于音频档位

对照 [后台验收矩阵](../testing/BACKGROUND_VOICE_ACCEPTANCE.md) 和 [连接协调器](../../app/src/main/java/io/github/ts3mobile/app/service/ConnectionCoordinator.kt)。需要新报告中的 `NETWORK_PENDING`／`NETWORK_CHANGED`／`NETWORK_UNAVAILABLE`、`RECONNECT_ATTEMPT`、`CONNECTED` 和终态失败类别，结合切换时间、是否锁屏及 VPN 状态。分开复现「无重试」「有重试但失败」「已重连但无音频」；只修证实的分支。重连后从新会话收新语音，不回放旧缓存；被踢、认证失败、用户主动断开和服务器身份限制不应被强行续连。不能把切网时没有语音数据的空窗当成缓冲故障。

## 首轮执行记录：诊断与隔离实验

- **接收 A/B（离线）**：使用真实接收队列、每路抖动与播放会话，替换为可区分包内容的合成解码器和 fake output。干净的 20 ms 包序列两档都逐样本送达，首写分别为 60 / 90 ms。把中间一个包额外推迟 75 ms，平衡档出现 1 次 PLC、1 个迟到丢弃；稳定档没有补帧或迟到丢弃，且逐样本完整。完全丢掉该包，则两档均需补帧。另测稳定档估算边界 70–160 ms。此结果只证实受控场景收益，长包、多人、实际听感和端到端延迟仍需专项对照；不开放设置，也不更改默认档。
- **可观测性**：诊断 JSON 追加 `OUTPUT_PERFORMANCE_MODE`（首个放行的已知路由上读取；0 普通、1 低延迟、2 省电）、`OUTPUT_RETIRED`（1 自然排空、2 路由未就绪、3 输出错误、4 失效命令、5 停止）及 `OUTPUT_CREATE_SLOW_MS` / `OUTPUT_START_SLOW_MS`（达到 30 ms 才记，值为毫秒）。退役原因是应用发起操作时的分类，不代表系统物理掉线，也不表示资源一定已释放。新字段使用原有的有界事件队列，故障标记仍有独立保留名额；不改采样列或音频内容采集。
- **蓝牙输出 A/B（待实机）**：从同一份代码先构建 A（默认），再用 `./gradlew -PbluetoothStandardOutputExperiment=true :app:assembleRelease` 构建 B。B 只在选中蓝牙、或系统路由此前已确认蓝牙时请求普通输出，首次路由尚未知的系统自动选择不强猜。两包接收档、缓冲申请值、48 kHz PCM、通话属性和防外放逻辑一致。Android 可以忽略性能模式请求；先从 JSON 确认两包实际模式不同，若两者都为普通模式，该次对照不能检验低延迟路径假设。
- **实机顺序**：先在低通话音量下对照首次进服和第一句语音，记录电音是否出现、是否所有讲话人受影响、以及静音反应。出现巨响立即停止收听，不要为了采样继续佩戴。安全后再标记并保存 JSON。此轮不同时修改路由就绪策略、不试更大的设备缓冲，也不变更后台网络重连。

## 接收缓冲体验包（历史）

从同一份代码构建 A（省略 `receiveStabilityExperiment`，平衡）和 B（`-PreceiveStabilityExperiment=true`，稳定优先）。
构建选项写入 APK 的布尔资源，播放器读取该值；交付前分别核对 APK 内资源值和真机报告值，避免增量构建误用旧常量。
两包使用相同包名、版本和原签名，用 `adb install -r` 交替覆盖；不改设置、编码、音频焦点、蓝牙输出和网络重连。
不要同时启用 `bluetoothStandardOutputExperiment`。新播放会话的 `RECEIVE_DELAY_PROFILE` 诊断事件值为 0／1，
分别对应 A／B；导出包含旧会话时不能混用，事件未保留时使用已核对的 APK 哈希和导出文件名识别档位。

同一手机、耳机、网络（含 VPN 状态）和发言源，按 A → B → A 各跑一轮。每次覆盖后重新连接，
听到断音立即标记，等 10–15 秒再导出，并按 A1、B1、A2 命名。分别比较断音和补帧/迟到、
应用内排队时间、播放欠载；不要把应用内延迟当作端到端延迟，也不要把真实丢失或 AudioTrack 欠载当作接收缓冲实验的收益。

## 体验版改动：首播保护与接收档设置

- 小米 14 同设备对照：TS3 均走同一 A2DP 输出且实际为低延迟轨道。冷启动 HAL `pal_stream_start` 阻塞约 1,113 ms，首轨清空了 3,844 帧且未消费；音乐暂停后约 0.9 s 加入，蓝牙仍处于播放状态，底层启动约 13 ms，首轨无需重建。
- 只给已确认蓝牙、已写入 PCM、但播放头未前进的轨道最多 1.5 s 起播窗口。窗口不延长正常写入超时，也不阻止硬错误、静音和路由失效立即退出。短语音的排空等待同样覆盖起播窗口；不做静音预热、不扩大队列。
- **设置 → 语音播放** 内保存平衡（默认）或稳定优先。连接中的变更由播放线程清空旧缓冲并重建输出；服务器、频道和上行采集不重连。两个档位和诊断值不变，替代旧 `receiveStabilityExperiment` 体验包参数；未保存的升级用户默认平衡，原 B 包用户可手动选稳定优先。`bluetoothStandardOutputExperiment` 仍是独立的工程诊断参数。
- 真机回归：待机后起播和媒体预热后起播各重复至少三次，确认首句与实际路由、`OUTPUT_RETIRED` 一致；再验证启动等待时断开耳机仍立即静音、前台视频音量不受影响，以及切换档位后同一会话内报告 `RECEIVE_DELAY_PROFILE=0/1`。
