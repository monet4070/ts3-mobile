# 持续开发计划

英文版：[CONTINUATION_PLAN.md](CONTINUATION_PLAN.md)

本计划把项目从当前的 M11 准备状态推进到已签名的生产 Beta 候选版本，再进入候选版之后的第一轮维护节奏。它不新增功能。耳语、语音激活、文字聊天、文件传输、权限管理、书签、应用内语言切换和多服务器标签页都不在范围内，除非另有决策记录（ADR-0002）。

验收标准仍是现有的
[M11 发布清单](M11_RELEASE_CHECKLIST.md) 和
[M10 稳定性矩阵](../testing/M10_STABILITY_MATRIX.md)。本文只给这些工作排期，不替代那两份清单。某一行执行完的当天，就在源清单上勾选，并附上脱敏证据。不要让本计划和那两份清单各说各的。

下文使用的状态：

- **完成** — 已实现，并且有自动化测试或有记录的真机运行。
- **部分完成** — 代码已有，但发布证据不完整或已过时。
- **未开始** — 尚未开始，或已经开始并明确推迟。

## 每一段都要遵守的规则

除了「只更新真机证据、不改代码」的情况，每一段对应一个 pull request。

1. 修改前先读本段会碰到的文件，以及对应的测试。
2. 只改本段需要的内容。不要把结构拆分和「真机矩阵已通过」写进同一次变更。
3. 每个行为变化都要新增或扩展回归测试。修 bug 要先有一个失败的测试。
4. 合并前运行「验证」一节里的自动化门禁。
5. 更新 `CHANGELOG.md` 的 Unreleased。用户可见行为或决策有变化时，同步更新 `README.md` 或对应 ADR。
6. 真机记录保持脱敏：只记设备类别、API 级别、路由类别、提交和结果。不记主机、密码、昵称、身份、频道名或参与者。
7. 如果某一段需要削弱测试、提交 `local.properties` 或记录密钥，就停下来。

## 验证

每次代码变更后，在干净的工作区运行：

```powershell
.\tools\check-build-environment.ps1
.\gradlew.bat quality :ts3-protocol:test :audio-opus:testDebugUnitTest :audio-opus:lintDebug :app:testDebugUnitTest :app:lintDebug :app:assembleDebug --stacktrace
.\tools\check-repository-privacy.ps1
git diff --check
```

改到原生音频时，还要在已授权的设备上运行：

```powershell
.\gradlew.bat :audio-opus:connectedDebugAndroidTest
```

候选版本那一段还要运行 `:app:assembleRelease`，并把 APK 的 SHA-256 记在仓库之外。

## 阶段 1 — 关闭 M11 真机冒烟

目标：M11 清单第 3 节，用当前 debug APK，在一台主要设备上完成。这是短门禁，不是 30 分钟那几行。

设备：一台 Android 10 或更新的手机。只记录设备类别和 API 级别。

- [ ] 冷启动，以及通知和麦克风权限流程，不崩溃。
- [ ] 连接、手动断开、手动重连。确认状态和频道快照属于新会话。
- [ ] 展开一个频道并看到成员。
- [ ] 双击一个公开频道，确认当前频道状态。
- [ ] 麦克风关闭、按住说话、常开。测完回到按住说话。
- [ ] 复制诊断导出，确认里面没有服务器地址、密码、昵称或身份。
- [ ] 再跑一遍原生真机套件（`connectedDebugAndroidTest`），记下通过数量。

结束条件：第 3 节勾选完成，并在 `docs/testing/M10_STABILITY_MATRIX.md` 的「Run log」下写一节带日期的脱敏记录。某一行失败时，先写成带回归测试的 bug，阶段 2 暂停，直到修好。

## 阶段 2 — 关闭带入 M11 的 M10 阻塞项

目标：M11 清单第 4 节。每次会话只跑一行，这样失败可以归因。使用专门配置的测试服务器和密码频道，不要用正式社区服务器。

顺序有意义。先跑长时间项，再改路由，这样简单场景里的崩溃会先被看到。

- [ ] **30 分钟扬声器双工。** 不崩溃、延迟不明显变长、麦克风不卡住。记录开始和结束时的延迟印象、电量、温度，以及脱敏后的诊断计数。
- [ ] **30 分钟熄屏。** 已有的 20 分钟不算。结束时前台服务仍在，通知栏断开可用。
- [ ] **密码频道恢复，5 次重连。** 回到上次频道，或者界面给出可操作的错误。策略单元测试不能代替这一行。
- [ ] **有线热插拔，10 次。** 拔出后回到系统路由，不崩溃。
- [ ] **蓝牙双工 15 分钟，再加上拔出回退。** 需要一只已连接的耳机。JVM 里的路由分类不能关闭这一行。
- [ ] **第二台设备，不同的 Android 代际。** 至少覆盖 Android 10、12、14 或 15，而不是另一台 Android 16。在那台上重复阶段 1 的冒烟，再加 15 分钟双工。

结束条件：第 4 节勾选完成，每一行有自己的运行记录。这时可以称 M10 完成。M11 还不行，要等到阶段 4。

这不是覆盖率百分比目标。下面这些生产类型今天出了问题，单元测试发现不了。

- [ ] 检查 release 清单。预期权限仍限于：网络、网络状态、音频设置、录音、发送通知，以及已经声明的三种前台服务类型。

结束条件：一个打了标签的候选构建，第二个人可以根据记录的 SHA-256 安装。应用仍是预发布。用户在重要服务器上仍应保留另一个客户端。

## 阶段 5 — 候选版之后的固定节奏

这是持续的部分。每周一个节奏。候选版经过一周真实使用之前，不开新里程碑。

| 何时 | 做什么 | 完成标准 |
| --- | --- | --- |
| 每次代码变更 | 运行「验证」里的自动化门禁 | 合并提交上命令退出码为 0 |
| 每周 30 分钟 | 在轮换设备上跑矩阵中的一行（扬声器、熄屏、蓝牙、有线、密码频道恢复） | 一条脱敏运行记录，通过或失败都要写 |
| 每周 | 在做任何功能之前，先处理这一行里的失败 | 每个确认的 bug 都有回归测试 |
| 每月 | 重读 ADR-0002 | 要么单服务器范围仍然成立，要么提出新的 ADR。没有新 ADR 就不开始聊天或书签 |
| 依赖升级时 | `--write-locks`，并复查锁定文件差异；fork 坐标不变 | 门禁和 `assembleRelease` 为绿 |

下面这些情况优先于每周节奏：

- 每周那一行里出现崩溃、麦克风卡住或过期会话，在回归测试覆盖之前，停止功能开发。
- JitPack 或 fork 不可用时，在产物能再次解析之前，停止发布构建。不要为了解阻塞去换一个随便更新的 ts3j。
- 任何把服务器密码、昵称或书签持久化的要求，都要先有新的 ADR。身份加密是唯一有意保留的持久化。

## 本计划不会做的事

- 不会凭 JVM 测试宣布 M10 或 M11 完成。
- 不会把 2026-08-16 的记录当成今天这个 APK 的通过结果。
- 不会在同一次变更里既 fork ts3j 又重构服务。
- 不会在真机行还没有证据时，靠加功能让 Beta「看起来更完整」。
